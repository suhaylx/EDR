# P0 milestone — cryptographic challenge issuance and constrained agent CA signing

**Status:** draft stacked change on PR #57; not merged, deployed, or production-approved. No untrusted endpoint is allowed to sign agent certificates or issue challenges.

## Implemented boundaries

1. **Issuer-only challenge creation**: `POST /issuer/v1/tenants/{tenant}/agents/{agent}/enroll/challenge` on the existing dedicated TLS 1.3 issuer listener, with required, verified issuer client certificate and pinned issuer fingerprint+tenant+actor grant. JSON body `{"ttl_seconds":300}` (60–600 seconds only). Success returns `challenge_id`, `challenge_secret` as base64, and `ttl_seconds` **only over issuer mTLS**. HTTP responses set `Cache-Control: no-store`; callers must not log or cache the secret. An unauthenticated client cannot call this route. A trusted issuer must deliver the one-time secret to the correct endpoint over an **independently approved secure provisioning channel**; that delivery mechanism is NOT implemented here.
2. **CSPRNG**: the Go `PostgresEnrollmentChallengeIssuer` uses `crypto/rand` for both RFC4122 UUIDv4 and 32 bytes of secret entropy, computes SHA-256, and sends **only the digest**, tenant/device, TTL and actor to PostgreSQL (the plaintext secret is not persisted). Database errors fail closed without exposing SQL. Issuers MUST revoke/rotate their pinned certificate grants if compromised.
3. **Database issuance**: migration `0007_enrollment_challenge_issuance.up.sql` adds a unique index restricting one unconsumed challenge per tenant/device, immutable-intent issuance/expiration audit and a `SECURITY INVOKER` DB function `edr_issue_enrollment_challenge`. The function locks the tenant row to serialize issuance with tenant disablement and initial enrollment, rejects already enrolled/revoked devices and disabled tenants, expires old pending challenges with audit, and atomically inserts the new digest plus issuance audit. It returns false for a still-outstanding challenge. A production migration **fails rather than silently deleting duplicate live challenges**; operators must investigate and reconcile preexisting duplicates.
4. **Constrained signing primitive**: `SignChallengeBoundAgentCertificate` accepts a controlled, external `crypto.Signer` and an explicitly verified agent CA certificate/root pool. It checks the signed challenge-bound PKCS#10 CSR, exact tenant/device URI SAN, CA public-key match with signer, CA cert-signing authority and validity, a bounded 1-minute-to-24-hour leaf lifetime, cryptographically random 128-bit serial, minimal digital-signature key usage and client-auth EKU. It verifies the resulting certificate's chain and public-key correspondence before returning DER. It is **not an endpoint**, never accepts a private key in HTTP JSON and does not create/store a CA private key. An HSM/KMS/PKCS#11-backed `crypto.Signer` is the intended controlled implementation.

## Mandatory trusted workflow

An authorized tenant operator provisions a named device and a one-time challenge via an issuer TLS client identity; the issuer transmits the secret to the device over an approved secured channel. The agent generates its **own private key**, includes the challenge-specific `ts-enroll-v1-...` Subject serialNumber and tenant/device SPIFFE URI SAN in a signed CSR, and returns only the CSR. The authorized issuer checks the PostgreSQL challenge and issuer permissions **before calling the signing primitive**. The leaf is then registered with its exact fingerprint through the existing `/enroll/complete` issuer endpoint; `edr_complete_agent_enrollment` atomically consumes the one-time digest and records the agent, certificate and audit. A certificate issued but not registered never authenticates to the EDR agent listener because that listener requires a matching enrolled SHA-256 leaf fingerprint.

**Important:** The signing primitive alone does not check the database or authorize a caller. It must never be exposed as a public HTTP certificate-signing service. Issuer credentials must be provisioned and rotated separately, issuer CA keys remain in approved key custody, and production operators must implement an authenticated device challenge-secret delivery channel. No Windows or Linux endpoint integration has been exercised.

## SQL operational notes

Apply migrations in order 0001–0007 using a dedicated migration role. `0007` depends on `0002` for append-only audit triggers and `0004` for the challenge table. A separately provisioned issuer DB role requires narrowly scoped EXECUTE on `edr_issue_enrollment_challenge` plus required SELECT/UPDATE/INSERT table rights, without schema ownership or SUPERUSER. Do not grant this function or challenge-table SELECT to the agent role or SOC frontend. Set PostgreSQL TLS chain/hostname verification, statement timeouts and bounded pools at service bootstrap. Audit triggers deter application-role edits but do not provide cryptographic tamper evidence against DB owners.

Local verification: `cd backend && go test -race -count=1 ./... && go vet ./...`; PostgreSQL integration: `EDR_TEST_DATABASE_URL=... bash scripts/test-enrollment-challenge-issuance.sh` against an **empty disposable** PostgreSQL 16 database. CI: `issuer-enrollment-security` and `postgres-challenge-issuance`, plus existing migration-chain workflow.

**Release gate remains closed** pending Agent 1 InfoSec threat-model approval (especially challenge delivery, rate limits, signer/HSM authorization, issuer certificate lifecycle, tenant separation and DB roles), Agent 3 independent QA including real TLS + PostgreSQL replay and race tests, and authorized Windows/Linux endpoint lab smoke tests. The localhost-only development bearer server must not be used as issuer or agent production identity.
